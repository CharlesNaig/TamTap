Project Overview

TAMTAP is a decentralized, locally hosted attendance management system specifically engineered for FEU Roosevelt Marikina. Operating exclusively over the school's Local Area Network (LAN), the system leverages NFC technology alongside automated camera verification to drastically eliminate proxy-attendance while maintaining sub-3-second transaction cycles.

2

System Flow Diagram

The architecture strictly follows a hardware state-machine model consisting of: IDLE → CARD_DETECTED → CAMERA_ACTIVE → SUCCESS/FAIL → IDLE. This guarantees a non-blocking asynchronous pipeline bridging the Python hardware core to the Node.js backend.

Hardware Components & Materials

The terminal is constructed from a mix of off-the-shelf electronics, power stabilization modules, and custom-cut housing. Below is the complete component manifest used during the build.

Image Component Category Purpose / Specification
Raspberry Pi 4 Model B Core Electronics 4GB RAM. Acts as the central processing brain, hosting the MongoDB database, Node.js server, and Python hardware scripts.
RFID RC522 Module Core Electronics 13.56MHz NFC reader for scanning student ID tags continuously with sub-100ms polling via SPI.
5MP Pi Camera V2 Core Electronics Captures automated facial verification snapshots instantly after card scans via CSI interface.
16x2 I2C LCD Feedback Blue Crystal type. Provides real-time terminal feedback (e.g., "Tap Card", "Access Denied").
Feedback IO Feedback Green/Red LEDs (with 330Ω resistors), tactile push buttons (Start, Restart, Stop), and an active buzzer (5V–24V) triggered via Power Relay.
UPS Module & Batteries Power Management Provides uninterrupted power featuring two 18650 Lithium Batteries (5,000mAh–7,000mAh) on a dedicated balanace platform.
Housing Structure Hardware Assembly Sintra board (main enclosure), Acrylic board (side panel), Hinges for rear maintenance doors, and Magnetic locks. Includes brushless cooling fan.
Interconnects & Supplies Hardware Assembly T-type GPIO extender, Breadboard, Jumper wires (M-M, M-F, F-F), Tapes (Masking/Electrical/Velcro), super glue, Soldering Iron.

SPI (RC522)

  • Pin 24 → GPIO 8 (CE/SDA)
  • Pin 21 → GPIO 9 (MISO)
  • Pin 19 → GPIO 10 (MOSI)
  • Pin 23 → GPIO 11 (SCK)
  • Pin 22 → GPIO 25 (RST)

I2C & General (LCD / LEDs)

  • Pin 03 → GPIO 2 (SDA)
  • Pin 05 → GPIO 3 (SCL)
  • Pin 11 → GPIO 17 (Green LED)
  • Pin 13 → GPIO 27 (Red LED)
  • Pin 12 → GPIO 18 (Buzzer)

Development Procedure

The development combined hardware assembly, backend engineering, and iterative field testing. The summary below compresses the full build experience from procurement to final optimization.

Components and Materials Used

Housing

  • Sintra board enclosure and battery balance platform
  • Acrylic side panel for component visibility
  • Hinges and magnetic locks for rear maintenance door
  • Brushless cooling fan for airflow control

Core Electronics

  • Raspberry Pi 4 Model B (4GB), RC522 RFID, 5MP Pi Camera
  • 16x2 I2C LCD (Blue Crystal), T-type GPIO extender, breadboard
  • Jumper wires (M-M, M-F, F-F) and 330-ohm resistors
  • Tactile push buttons (Start, Restart, Stop)

Feedback and Power

  • Green/Red LEDs, active buzzer (5V-24V), and relay control
  • UPS module with two 18650 Li-ion batteries (5,000mAh-7,000mAh)
  • USB SD Card reader for flashing and maintenance

Assembly and Tools

  • Soldering iron for RFID pins, LEDs, and wire joints
  • Masking tape, electrical tape, super glue, Velcro tape

Development Process

Step 1

Funding and Material Acquisition

The build started with pooled funding and staged hardware purchases. Priority was given to core test parts: RFID, LCD, buzzer, relay, jumper sets, Raspberry Pi, and soldering tools.

Step 2

Individual Component Testing

Each device was validated using dedicated Python scripts: NFC ID reads, GPIO LED outputs, relay-driven buzzer logic, LCD communication, and camera capture. Dependencies and setup commands were documented during this stage.

Step 3

Hardware Integration and Main Controller

After passing isolated tests, all modules were wired together. The separate test scripts were consolidated into one main hardware controller to coordinate the full attendance cycle.

Step 4

Database and Reliability Layers

Schemas were built for students, teachers, schedules, archive schedules, and hardware status, with encrypted teacher credentials. Continuity was improved through fallback storage layers centered on local MongoDB and local JSON backup, including prototype cloud-mirror testing during development.

Step 5

Synchronization and Emergency Controls

The hardware loop was synchronized with backend writes, followed by repeated debugging for attendance accuracy. Physical Start, Restart, and Stop buttons were added for manual recovery in case of runtime issues.

Step 6

Auto-Start and Full Web Platform

A Raspberry Pi service was configured for automatic startup on boot. The web system was then completed with Express.js, sessions, MongoDB integration, Socket.IO, role-aware middleware, and the full page set (Login, Dashboard, Admin, Privacy, Terms, Researchers, and 404).

Step 7

Final Optimization

Final tuning focused on loading speed, asset compression, and smoother dashboard startup performance, especially for first-time access on school LAN clients.
